# 按目标完成一个功能

第三方开发的起点是用户行为，不是先选一个钩子。这里把“目标 → 契约 → 实现 → 证据”应用到 XSR，避免做出能演示却不能可靠使用的扩展。

## 第一步：写出能判断真假的目标

差的目标：“做一个高级主题。”可验收的目标：“用户在外观页调节字号，释放滑块后当前标题更新；切换亮暗模式仍可读；重启保留值；清单错误保留上一主题。”后者同时说明入口、结果与失败行为。

用下面的短表记录一个功能，不需要先设计庞大框架：

| 项目 | 必须回答的问题 | 主题示例 |
| --- | --- | --- |
| 触发 | 谁在什么时候做什么？ | 用户拖动标题字号滑块 |
| 当前事实 | 谁拥有真实值？ | Host 持久化的当前主题选项 |
| 结果 | 从哪里能观察成功？ | 标题字号与重启后读回的选项 |
| 边界 | 哪些行为不属于这个功能？ | 不改变业务按钮或安装图标 |
| 异常 | 失败、离页、重试时怎么办？ | 保留草稿及最后有效样式，允许再保存 |
| 证据 | 什么测试足以证明？ | 浅/深色、滑块、坏值、重启各一例 |

## 第二步：确定归属与上游契约

先查当前实现，不按类名猜行为。对每项需求确认：

- 已有样式能力可完成吗？能则使用 NTP，不启动额外进程。
- 需要新行为吗？在 Sidecar 私有逻辑中实现，通过声明的命令和状态与 Host 交换。
- 需要展示吗？选择已授权的模块槽与有限文档；不把 Host API 当成页面脚本接口。
- 当前目标未开放吗？先说明缺口和所需契约，向 Host 工程提出目标与测试；不能通过反射、任意文件或未授权钩子绕过。

架构设计可能描述未来能力。要在当前标签找到类型、准入、消费者和测试，才能写“已支持”。一个枚举值存在并不证明某个页面会执行它。

## 第三步：把通信分成四种职责

以“提交便签并在资源扩展卡片显示”为例：

| 需求 | 合适的契约 | 为什么 |
| --- | --- | --- |
| 用户提交新便签 | `Command example.note.set`，UTF-8 参数 | 请求副作用，需要验证与完成结果 |
| 始终显示最后有效便签 | `State example.note.current`，UTF-8 | 新页面也能立即读当前值 |
| 显示操作可用性 | `State example.note.enabled`，Boolean | UI 消费事实，不自行推断进程健康 |
| 告知一次成功提交 | `Event example.note.changed` | 已发生的瞬时事实，不能代替当前便签 |
| 一次性计算便签摘要 | Query，仅确有该需求时添加 | 请求一个结果，不在每帧循环调用 |

不要为每个界面属性发明查询。当前状态会通过注册快照进入 Host 本地镜像，绘制无需往返 IPC。

## 第四步：完成一个纵向闭环

第一版就包含输入验证、注册、初始快照、激活、一个真实命令、状态更新、取消与退出。把 UI 画完、返回硬编码成功、以后再补权限和错误处理，不是闭环。

推荐实现顺序是：先业务与值契约，再编码/解码，随后生命周期与本地自测，然后有限 UI，最后原生包和签名准入。每一步都服务同一个目标，不同时改造不相关模块。

## 第五步：选能发现错误的验证

| 情况 | 必须观察的结果 |
| --- | --- |
| 正常提交 | Command 成功，State 为新值，界面显示一致 |
| 参数无效 | 明确失败，原值不变，不伪装成空成功 |
| 用户离页 | 旧 exposure 的点击和完成结果失效 |
| 会话停止/重启 | 未完成交换结束，旧数字 ID 不复用，新快照后再激活 |
| 高速重复输入 | 有界队列或合并策略，不无限增长 |
| 资源缺失 | 按声明回退或拒绝激活，保留有效展示 |

测试应验证行为，不只断言某个私有方法被调用。协议回环可证明编码，真实子进程自测可证明 IPC，正式安装验证才证明签名与生产准入。清楚写出证据层级。

## 什么时候停止，什么时候扩展

验收标准通过后，记录已知限制并交付。新增需求再开一个有边界的功能单元。遇到无关问题，记录位置、证据和影响，回到当前目标；只有它阻碍本功能或造成实际风险，才纳入当前修复。
