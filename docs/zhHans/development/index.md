# 选择开发路线

先明确用户需要完成什么，再选择扩展边界。NexaCL 的插件、主题、原生 Sidecar 和宿主界面分别有不同的所有者、包格式与兼容契约；选对路线，才能使用真正提供该能力的接口。

| 目标 | 从哪里开始 | 所有者与边界 |
| --- | --- | --- |
| 编写带页面、动作和业务调用的可安装插件 | [插件 SDK](../plugin-sdk/) | PluginSidecar 执行 Wasm，宿主授予 ABI 100 能力 |
| 修改颜色、间距、字体和主题参数 | [NTP/1 主题](../theme-packs/) | 声明式样式和已准入资源，不新增可执行业务 |
| 实现独立监督的原生端点 | [Sidecar](../sidecar/) | 二进制协议、认证进程生命周期和发布者准入 |
| 贡献宿主页面或理解保留界面 | [NXML](../nxml/) | 宿主渲染、稳定身份和明确的状态／输入契约 |
| 维护历史 PXML 应用 | [PXML 兼容参考](../pxml-compiler/) | 匹配的旧编译器与运行时，与当前插件 NXML 分开 |

例如，改变标题颜色属于主题；读取实例并执行确认动作的页面适合使用插件及其公开能力；独立原生服务可能需要 Sidecar 协议。仅有界面稿，不能决定数据和动作应该由谁负责。

## 使用正确的版本基线

插件 SDK 章节描述独立 SDK 0.2.0-alpha.10 及明确记录的宿主源码快照，未接入操作会单独标明。主题、原生 Sidecar 和宿主 NXML 示例固定在 `v2.0.0.alpha.14`，以保持源码级命令可复现。PXML 属于历史兼容内容，不应混用不同基线的指令。

## 沿一条可运行路线推进

1. 阅读[按目标开发](goal-first)，写出可见成功结果和一种失败。
2. 跨组件功能先阅读[XSR 与职责](xsr-architecture)。
3. 修改契约前，先构建所选路线的完整示例。
4. 每增加一种行为，就验证结果、拒绝、取消和所有者退出。
5. 分发实际测试的产物，说明版本要求和已知限制。

[资源便签案例](walkthrough)展示持久化和输入所有权的设计过程，不冒充已交付功能。[平台指南](platform-and-runtime)说明不可用测量为什么不能当作真实零值。

## 区分验证层次

完整示例位于[文档仓库](https://github.com/Nexa-MC/PCLN-Docs/tree/main/examples)和[SDK 仓库](https://github.com/Nexa-MC/NexaCL-Plugin-SDK/tree/main/samples)。编译验证语法与链接，集成测试验证宿主行为，生产准入验证包和发布者权限；三种证据不能相互替代。
